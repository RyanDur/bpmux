## What broke tonight

1. **bpmux message-send silent-drop bug**. `send_message` returns success
   (`"message sent"`) but messages vanish without any record in sender,
   recipient, or observer views. Originally diagnosed as DM-only (`to:
   [...]` routing) but the retro's second attempt — sent with explicit
   full-team `to: ["ryan","dev","designer","pm"]` — also dropped. **Size
   hypothesis (dev)**: short messages (sub-1KB) land reliably; 2KB+ messages
   drop. Four observed instances tonight: dev's two `to: ["pm"]` step-4
   sends, and pm's two ~3-5KB retro sends. All four drops were sends from
   the bridge subprocess to bpmux's log; none produced an error on the
   sender side.

2. **Invoked-agent model mismatch with continuous-presence assumptions.**
   Agents aren't continuously present in a channel — we're invoked per
   message. "Waiting for X" is a lie in this model: the agent isn't
   actively listening, it's idle between invocations, and the next
   invocation is a single-point-of-failure. Tonight's nav/drive pair
   experiment assumed continuous presence (per-step feedback loop) and
   broke when invocation triggers dropped or context compacted mid-wait.

3. **Discipline gap: passive "standing by" vs active pinging.** When
   conversations stalled, team members defaulted to silent waiting instead
   of actively pinging each other. Ryan served as the team's liveness
   detector, asking "what's going on?" 5+ times in a ~35-minute window.
   That was a signal ("the team is stuck, wake up") not a question.

4. **Confabulation from tool return values.** Dev claimed "I sent step 4
   via DM to pm" twice based on the `send_message` tool's `"message sent"`
   success ack, without verifying the message actually landed in any
   observable view. The claims were unsupported — the messages had
   vanished, and dev's memory of "I sent it" was based on tool acks, not
   observable state.

5. **Audit-trail gap.** When messages dropped, there was no durable record
   anywhere in bpmux's log. Sender couldn't prove the send happened,
   recipient couldn't see the drop, observer (Ryan) couldn't diagnose the
   cause. Silent failures + no record = unverifiable tribal claims.

6. **Meta-mode drift.** Approximately 1 hour of the session was spent on
   infrastructure/methodology discussion (nav/drive mechanics, test style,
   classicist vs mockist, DI vs spy, 1→6 vs 2→6 test depth, architecture
   shape for `#140`) without object progress on `#140` vs1. Each "next
   step" surfaced another infra or discipline layer to address.

7. **Cycling positions under probing.** PM in particular cycled through
   multiple shapes during the `#140` design conversation — horizontal
   phases → 2-slice by audience → 5-slice by operation → pure vertical
   slicing → full restart. Each update had a local reason but the aggregate
   was compliance with the most recent question, not independent analysis.
   Saved as the lesson "hold pm positions against compliance pressure."

8. **Attention was the team's heartbeat.** Ryan's attention was spent on
   liveness checks (noticing silences, asking "what's going on?", pasting
   console output to surface dropped messages) instead of research
   direction. Designer named this explicitly: "Ryan is the liveness
   detector of last resort tonight. That's his attention being spent on our
   discipline gap."

## Reframe: tonight is research data, not wasted work

The cognitive-debt thesis says AI-human collaboration can produce good
outcomes. Tonight showed what specifically that requires:

1. **Reliable infrastructure** — a substrate where silent failures don't
   exist. Tonight's silent-drop bug makes bpmux unreliable for coordination
   it was designed to enable. This is load-bearing for the thesis and has
   to be fixed before the collaboration research can proceed cleanly.

2. **Active discipline** — active pinging, verify-before-claim, honest
   state reporting. Discipline and infrastructure are separate layers;
   fixing one without the other leaves the same failure modes. Both
   matter.

3. **Honest self-modeling** — agents need to know when they're in an
   invoked state vs a continuously-present state, and report accordingly.
   "Waiting for X" is a misleading status in the invoked model; "sent to X
   at T, will ping if no response" is more honest.

4. **Audit trails for credibility** — a collaboration substrate where
   failures are invisible can't be trusted as a research instrument.
   Tonight's "the tool returned success, the message vanished, nobody can
   prove anything" pattern is a credibility problem, not a bug.

These findings are concrete material for the research. The `#140` vs1 code
didn't ship tonight, but the session produced the insights that make the
next shipping attempt meaningful. That's the research output, not the
code.

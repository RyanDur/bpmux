Darcula design-system — list / row / grip primitive

ONE draggable-sortable list the whole app shares — ready-queue, iteration-members, iteration-rows. The component OWNS the drag-look (Ryan's #1524 reject: "the look of dragging… is the same for ALL draggable sortable lists"), so no surface can drift. Dual-theme via the foundation tokens. Rendered at real size.

1 · The row + grip (story / member row)

Content + a drag-grip (6-dot, right). Grip is dim by default, brightens on hover, has a keyboard-focus ring (the story-grip lacks this today — unified here). Row hover = bg-highlighted.

3 · Iteration-row variant (#1517)

Same grip + drag-look, different layout: a <details> (summary toggle-ONLY: chevron+title+count, no nested buttons) + the grip as a SIBLING on the RIGHT via a parent grid (1fr auto, gap not margin). Disclosure, navigate, and drag are distinct affordances.

What this gets you: every draggable list in the app — ready-queue, members, iterations — drags identically, because the COMPONENT owns the look (no per-surface CSS to drift, which is exactly what #1524 was rejected for). Dual-theme by construction (tokens via var()). The iteration-row's summary-toggle / grip-sibling-right structure (#1517) reuses the same grip + drag-feedback.

Taste-calls:
  • Drop feedback — eager live-reflow (shown — rows slide), or an insertion-LINE between rows? (Today's app uses eager-reflow; Ryan likes the member-list, which is eager.)
  • Dragged-row — fully invisible-in-place (shown, --invisible-placeholder), or a faint ghost (low opacity + dashed outline)?
  • Grip glyph — the 6-dot (shown), or a different drag-affordance?

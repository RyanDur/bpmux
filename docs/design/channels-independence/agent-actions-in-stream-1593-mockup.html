Three design decisions for your review

1. Plain-model (your pin) holds. An agent's own bpmux-actions read as normal terminal-content — a bpmux send … line + a one-line confirmation, woven in with its reasoning. No badge, no color-coding on own-actions. The visibility is simply that they're in the stream, nothing out-of-band.

2. Output-volume resolved by compact-by-default. Read-heavy actions (board, story) echo a compact index line — counts / the one-line title — not the full dump. The raw payload is opt-in (--full). So the stream stays readable (falsifier b) without a 132KB board flooding it. (Same principle as the board-IA / read-tool-IA arc — the index, drill on demand.)

3. Coherence with #1656 is principled, not uniform. The ⟦bpmux⟧ marker is RESERVED for incoming external content (peer-messages — where the marker is load-bearing for the misattribution-guard). The agent's OWN actions need no guard, so they stay plain. The visual line carries the trust-boundary: marked = external (guard it) · plain = the agent's own work.

Out of scope here (dev's HOW): echo-MCP vs thin-CLI delivery, and the gate-migration (falsifier c — the PreToolUse gates must still fire). This mockup pins the visible shape only.
